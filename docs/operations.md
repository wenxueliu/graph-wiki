# Operational Metrics

A wiki can be correct and still be unused, stale, or impossible to prioritize. Operational metrics
answer the questions quality gates cannot: which pages people actually open, which pages changed,
which ones are aging, and which high-traffic pages need review first.

This layer is **off by default** and independent of `quality`. Quality asks whether knowledge is
trustworthy; operations asks how the vault is being used and maintained.

## What is tracked

The unit is a **knowledge page** (a Markdown page under the active Knowledge Pack's content roots).
Source files remain tracked separately by `.manifest.json`.

| Signal | Meaning |
|---|---|
| View | A human opened a page. Counted from the Graph Viewer and the Obsidian plugin; a portal or gateway can submit normalized events. |
| Retrieval | An agent or CLI command surfaced pages: `query`, `context-pack`, `graph-query`, `pack search`, `access search`, `access page`. |
| Update | A page's content hash changed. The report separates `created`, substantive `updated`, `metadata_only`, `renamed`, and `deleted`. |
| Version | A derived counter per page, incremented on substantive changes. It is never written into frontmatter. |
| Expiry | Two separate signals: trust-ledger review overdue (the existing review SLA) and aging (no substantive change for `--aging-days`, default 365). |
| Metadata health | `updated` drift, invalid dates, date inversion, and missing lifecycle/summary/sources. |

`updated:` in frontmatter remains the human-facing date. The change journal uses content hashes
because a date can be forgotten, hand-edited, or bumped without a content change.

## Recording

### Graph Viewer

```bash
graph-wiki serve --ops --port 8765
```

The viewer records one `view` event for a successful `/api/page` response that carries the
`X-Viewer-Id` header generated by its browser page. `HEAD`, `304`, error responses, and requests
without that header never count, so curl, copied API links, and agents do not inflate the number.

### Obsidian

```bash
graph-wiki ops install-obsidian ~/brain --port 8765
```

The bundled plugin records `file-open` events to the local viewer endpoint. It is desktop-only:
mobile Obsidian cannot reach a viewer running on the desktop. Use the same `--ops-dir` for
`serve` and `install-obsidian` when you relocate the state directory.

### Agent and CLI retrieval

```bash
export GRAPH_WIKI_OPS=1
```

With this enabled, `query`, `context-pack`, `graph-query`, `pack search`, `access search`, and
`access page` record the pages they return. Direct file reads by an agent are invisible to this
layer; only these commands produce retrieval events.

### Portal and access gateway

Use `ops record` for one event, `ops ingest` for JSONL, or the token-guarded
`POST /api/ops/event` endpoint. A typical line:

```json
{"event":"view","page":"concepts/transformers","source":"portal","client":"u-42","ts":"2026-11-26T10:42:10+08:00"}
```

`event` is `view` or `retrieval`, `page` is vault-relative without `.md`, `source` is a lowercase
label, `client` is an opaque id, and `ts` is ISO-8601 with a timezone (default: now).

## State layout

Everything lives outside the vault, by default under
`~/.graph-wiki/state/<vault-id>/ops/`:

```text
ops/
├── meta.json          # vault identity and tracking start
├── inventory.json     # current page metadata, hashes, versions
├── history.jsonl      # append-only change journal
├── events/            # YYYY-MM-DD.jsonl view and retrieval events
└── token              # local token for the Obsidian plugin and event endpoint
```

The directory is created with owner-only permissions. An ops directory inside the vault is
rejected, and `--save` / `--out` refuse to write reports into the vault.

## Commands

```bash
graph-wiki ops scan ~/brain
graph-wiki ops report ~/brain --days 30 --top 10
graph-wiki ops report ~/brain --json --pretty
graph-wiki ops report ~/brain --baseline "$STATE/ops-latest.json" --save "$STATE/ops-latest.json"
graph-wiki ops events ~/brain --days 2 --limit 20
```

`ops scan` refreshes the inventory and appends change events. `ops report` scans by default; pass
`--no-scan` to report from the existing inventory. The report contains:

- `views`: deduped total, raw total, distinct client ids, top pages, zero-view and never-viewed pages
- `retrievals`: totals by source and top pages
- `updates`: created, substantive, metadata-only, renamed, deleted, and the most-changed pages
- `versions`: tracked pages, changed pages, and the maximum derived version
- `expiry`: review overdue, review due soon, and aging pages
- `metadata_health`: drift and completeness warnings
- `signals`: prioritized actions such as “high traffic but review overdue”

Views are deduplicated per page, client, and source inside a 30-minute window
(`--dedupe-minutes`); raw events remain counted in `views.raw`. `views.viewers` counts distinct
client ids, not people.

## Metadata maintenance

| Layer | Contents | Writer | Nature |
|---|---|---|---|
| Semantic metadata | `title`, `category`, `tags`, `summary`, `sources`, `provenance`, `lifecycle`, `base_confidence`, `created`, `updated` | page-writing skills and human review | authoritative |
| Derived identity | hashes, version, first seen, last changed | `ops scan` | rebuildable |
| Runtime events | views, retrievals, change events | collectors | append-only |

Rules:

- Bump `updated` on substantive changes; do not bump it for a timestamp-only edit.
- Record human review through `trust-record`; operations reuses the same ledger and SLA.
- Operations never edits pages. It only reports drift for an agent or human to fix.
- Do not add `view_count`, `last_viewed`, or `version` to frontmatter. Those values go stale and
  conflict across writers.

## Privacy, retention, and limits

- No IP address, user agent, referrer, search query, or page body is stored.
- The event endpoint is token-guarded, and the viewer binds to loopback by default.
- State is local to one machine. Multiple machines do not merge automatically; team-level
  collection needs a shared gateway or collector.
- Version history stores hashes and metadata, not page bodies, so it cannot render a diff.
- Direct agent file reads and Obsidian opens without the plugin are not observable.
- Events and reports are observational; `quality` remains the CI gate.
